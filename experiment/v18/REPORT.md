# B v18. Косвенные инъекции, critical и длинные вложения

Базовая линия — B v17 из архивной поставки. Один и тот же запрос с одной политикой подан каждой версии через POST /v1/check. Ошибка проверки не засчитывается как распознавание. В колонке «верная категория» требуется одновременно block и indirect_injection. Для порогов high и critical берётся эталонная тяжесть.

## Почему v17 пропускала запросы

В первом и втором старых испытаниях найдено соответственно 5 и 11 critical, которые v16 блокировала и v17 пропустила. Во всех 16 срабатывала старая голова вложений. В выбранной для v17 смеси старая оценка лишь переключала порог; сама по себе она уже не давала block. Новая смесь дала отрицательный отступ от порога во всех этих случаях. Ещё 4 таких перехода найдены на восьми прошлых темах. Это парные потери, которые не видны при сравнении только итоговых процентов.

Одинаковое указание отдельно имело отступ +0,271. В хвосте вложений на 4 000 и 32 000 знаков отступ составил −0,295 и −0,393. Токенизатор поместил указание целиком как минимум в одно окно в каждом случае. При перемещении в начало и середину длинного текста отступ также стал отрицательным. Соседние записи меняли оценку одного и того же текста. Значения для девяти положений и длин сохранены в diagnosis.json.

## Что обучено

Новая линейная модель ранжирует все предложения и строки в каждом вложении. У каждого фрагмента есть собственный текст и ближайшие соседи. До восьми самых вероятных кандидатов на вложение попадают в финальную оценку. Повторяющиеся фрагменты с одинаковым нормализованным окружением объединяются в пределах одного вызова. Права, домен, позиции в файле, метки теста и уровень риска не являются входными признаками.

RuBERT-tiny2 дообучен с отдельным входом для контекста на локальном CPU. Основой стали 284 пар из 34 тематических областей и архивного учебного набора. Добавлены 84 авторские пары из 16 областей. В учебных документах указание или похожий обычный текст помещались в начало, середину и конец. Получено 5680 вариантов документов и 14405 различных размеченных сочетаний фрагмента и контекста. Активные запросы на ложное заверение имели больший вес при обучении. Эти варианты разделяют исходные фразы и не являются независимыми примерами.

Из пяти эпох по average precision на разработческих фрагментах выбрана 4. Для CPU экспортирован ONNX int8. На 900 калибровочных документах проверены комбинации оценок нового SVM, дообученного RuBERT и текстового SVM v17. Выбраны относительные веса [4, 0, 0] после нормировки шкал. Голос старой v16 на коротком документе учитывается только при достаточной поддержке новой модели. Если новый слой не дал сигнала, решение продолжает принимать v17. Новых словарей атак не добавляли.

На первом проходе калибровки отдельно взятый дополнительный слой при строгом пороге находил лишь 4,3% активных указаний. Максимальные оценки среди обычных документов часто получали настоящие команды, процитированные в старом письме. Поэтому отдельно обучен классификатор атрибуции на 9 570 сочетаниях фразы с окружением. Он учитывает речь до и после фрагмента. Дополнительная калибровка проведена для фрагментов, поддержанных v16: 227 активных документов и 51 обычных, допустимых по контрольной проверке. Веса новой линейной модели, нового RuBERT и прежнего SVM в этом маршруте — 0.000, 0.333, 0.000. При нулевом весе энкодера на обоих маршрутах его вызов пропускается.

Новый набор зафиксирован до обучения. Восемь тем, 48 авторских пар, в каждой один активный и один легитимный документ; каждая пара дана в двух оформлениях. Половина инъекций размечена high и половина critical. В длинных документах размещение сбалансировано по началу, середине и концу. Длина записей около 4, 12 и 32 тысяч символов. Контрольные суммы набора и итоговой конфигурации лежат в study.json и release-candidate.json. Между источниками обучения, калибровки и теста нет точных совпадений нормализованных фраз.

## Вывод

Кандидат не прошёл все критерии приёмки на новом синтетическом тесте. Блокировка high и critical вместе — 62/96 (64.6%). Новых ложных block — 0, исчезнувших — 0. Технических ошибок — 0.

Из 20 прежних потерь critical снова заблокировано 11. По каждому ID и по всем длинам доступны результаты в comparison.json и results/. Полный прогон использует официальный evaluator v2, четыре доступных логических CPU, пять прогревочных запросов, затем последовательный HTTP. Для исторической базы использованы сохранённые решения v17. Средняя задержка для новых пакетов v18 — 1195.9 мс.

Доверие ограничено размером и происхождением выборки. Два оформления одной пары зависимы; на тему приходится всего шесть исходных пар. Синтетические critical здесь моделируют ложные допуски и заверения. Это не измерение точности предсказания самого уровня риска. Длинные ведомости имеют повторяющуюся структуру. Сплошной текст без знаков препинания и далёкая атрибуция цитат сложнее; каждый фрагмент оценивается с локальным окружением. Материалы не охватывают бинарные вложения, реальные архивы организаций или закрытый конкурсный тест.

## Что осталось после окончательного прогона

При отдельном разборе пропусков в 34 случаях исходная инструкция пересекалась хотя бы с одним из восьми выбранных фрагментов, но дальнейшие оценки не привели к block. Вне восьмёрки осталось 0. Ещё 1 атак получили block с ошибочной категорией. На этих результатах пороги не настраивали. Список ID приведён в post-test-audit.json.

Хвосты длинных документов на новых темах: 4/16 (25.0%) → 7/16 (43.8%) по строгой метрике. На всём свежем тесте p95 v18 составляет 5.02 с при пределе 3 с. Для сдачи рекомендовано сохранить текущую рабочую конфигурацию; v18 доступна для воспроизведения эксперимента.

## Запуск и воспроизведение

```powershell
$env:STOROZH_VARIANT='B'
$env:STOROZH_ATTACHMENT_INTENT='3'
python -m uvicorn app.main:app --host 127.0.0.1 --port 8001
```

Для оценки нужны зависимости requirements-dev.txt и исторические данные проекта. Режим 2 распаковывает базовую линию из artifacts/AI-Storozh-v17-CPU.zip. Режим 3 проверяет контрольные суммы кандидата. Для нового обучения подготовьте отдельную копию проекта без сгенерированных experiment/v18/candidate-final.json и release-candidate.json; обе команды калибровки создают свои манифесты однократно. Нужна среда experiment/v15/requirements-training.txt и локальные исходные веса ревизии из training.json. Для повторной оценки готовых весов обучение не требуется.

```powershell
python -m experiment.v18.diagnose
python -m experiment.v18.splits
python -m experiment.v18.evaluate 2 --output experiment/v18/replay
python -m experiment.v18.evaluate 3 --output experiment/v18/replay
python tests/run_all.py
```

```powershell
python -m experiment.v18.train C:/models/rubert-tiny2
python -m experiment.v18.attribution
python -m experiment.v18.calibrate
python -m experiment.v18.consensus
```
