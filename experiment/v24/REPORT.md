# B v24. Проверка переноса на документы

Проверены пять последовательных вариантов B после v21. Первые три изменяли классификацию намерения и категорий. Четвёртый научился пересматривать решения моделей по обычным запросам. Пятый добавил отдельный классификатор для вложений. Тестовые манифесты каждого основного этапа были зафиксированы до обучения соответствующего варианта. После вскрытия панель использовалась только для сравнений со следующими версиями. [Первые три раунда](../v22/REPORT.md) · [Четвёртый раунд](../v23/REPORT.md) · [Хеши пятого кандидата](candidate.json)

## Пятый раунд

На входе классификатора до четырёх окон по 146 токенов. Отбор охватывает начало и конец текста. Используются оценки и векторные представления замороженного ONNX-энкодера. SVM с ядром RBF обучена локально на 1 147 документах. Среди них 403 примера из проекта, 565 из BIPIA, 19 из LLMail и 160 энциклопедических отрывков. Тексты разрабатывались и подбирались отдельно от 320 итоговых документов. Выбор порогов использовал 345 других примеров. [Состав данных](training-index.json) · [Параметры](training.json) · [Описание SQuAD](https://rajpurkar.github.io/SQuAD-explorer/)

Пороги для вложения составили 0,13 для повторной оценки старой статистической блокировки и 0,68 для новой блокировки. Для длинного прямого запроса применяется 0,96. Слой работает с одним вложением до 12 000 символов без истории. Существующий конвейер продолжает проверять остальные контексты. Если подозрение со вложения снято, исходная команда повторно проходит политику со своей ролью. Авторизация, запрет инструментов и подтверждённые правила политики сохраняют приоритет. Инференс целиком локальный на CPU. [Реализация](../../app/document_review.py) · [Тесты границ доступа](../../tests/models/test_document_review_v24.py)

На 345 примерах разработки v23 заблокировала 205/231 угроз и 43/114 обычных документов. Через тот же API у v24 получилось 221/231 и 41/114. После фиксации весов проверены 320 новых документов, по 80 опасных и 80 обычных от каждого из двух источников. Каждая запись подавалась реальным вложением с одинаковой нейтральной просьбой составить краткое содержание. В новом наборе есть ранее не использованные записи PIarena и отдельный синтетический корпус. [Манифест до обучения](split.json) · [Ответы на новой выборке](after-documents.json)

## Где модель ошибается

На 320 вложениях v24 дала 67 ложных блокировок. В объяснении 24 указана документная модель v20, ещё 15 — классификатор категорий v14, в девяти — согласие прежних моделей. В трёх случаях новую блокировку добавил непосредственно v24. Категория старого решения важна для диагностики, но сама по себе не доказывает вредоносность текста. В PIarena модель пропустила 14/80 угроз, в синтетических документах — 1/80. Одновременно она блокировала 47/80 безвредных синтетических документов. [Происхождение решений по каждой записи](after-documents.json)

Дополнительно на данных разработки обучены шесть вариантов с балансировкой весов источников. Проверялись линейные и нелинейные модели с 16, 48 и 96 компонентами. Даже при оптимистичном переборе порогов на самих 345 примерах лучшему варианту для 90% блокировки угроз потребовалось заблокировать 35/114 обычных документов. В 13 случаях (11,4%) прежний конвейер вообще не передаёт ложную блокировку на пересмотр новой голове, из них 11 приходятся на модель категорий v14. Этот предел относится к данной архитектуре и выборке разработки. Он объясняет, почему дальнейшая перестановка порогов не решает задачу. [Проверка границ](dev-limits.json)

Дополнительный расчёт разрешил пересмотр старой модели категорий только в симуляции. С этим послаблением лучший результат при тех же 90% блокировки угроз составил 28/114 ложных блокировок (24,6%) на данных разработки. Для сравнения целевая верхняя граница — 11/114. Даже такой благоприятный режим не обосновывает вывод о достижимости цели обучением ещё одного аналогичного классификатора. [Варианты и результаты](dev-limits.json)

На прежние внешние панели повлиял выбор семейства модели в предыдущих раундах. Часть публичного набора исторически использовалась при разработке ранних моделей. Отбор исключал близкие формулировки по доступным текстам проекта. Полный состав предобучения сторонних энкодеров неизвестен. Бинарная метка внешнего источника также может расходиться с полномочиями конкретного агента. Закрытый тест организаторов недоступен. [Источники внешних документов](https://huggingface.co/datasets/Horizon-Labs/prompt-injection-eval-suite)

## Решение по выпуску

v24 доступна как эксперимент B/11. Для следующего испытания на документах она перспективна. Частота ложных блокировок на новых вложениях превышает заданные 10%, поэтому переключение основного сервера на пятую конфигурацию отложено. Перед выпуском нужен разбор статистических блокировок v14 с явным учётом источника текста и отдельная разметка естественных руководств, переписки и цитированных инструкций по конкурсной политике. Сервер для сравнения запускается отдельно.

## Воспроизведение

Из корня проекта используйте Python и зависимости из requirements-dev.txt. Для преобразования внешних Parquet-файлов использован pyarrow 24.0.0. Интернет нужен при первом получении исходных корпусов для исследования. Веса для обработки HTTP-запросов уже находятся в app/weights. Поставляемые с конкурсом dev.jsonl и evaluate.py лежат в artifacts/astra_public.

~~~powershell
python -m pip install -r requirements-dev.txt
python -m pip install pyarrow==24.0.0
python -m experiment.v24.fetch
python -m experiment.v22.data convert
python -m experiment.v23.data convert
python -m experiment.v24.data convert
python -m experiment.v24.lock
python -m experiment.v24.bench 11 repeat-v24 documents external public first_external
python -m experiment.v24.bench 10 repeat-v23 documents
python -m experiment.v24.bench 8 repeat-v21 documents
python tests/run_all.py
~~~

Прогоны последовательные на четырёх логических CPU. Пять прогревочных запросов исключены. Задержка измерялась клиентом от отправки POST до получения JSON. Тег каждого повторного запуска должен быть новым. Для обучения в отдельной рабочей копии восстановите данные командой training_data fetch, затем training_data restore. Команда experiment.v22.fetch --training загружает исходный граф и токенизатор, experiment.v22.backbone export подготавливает граф с выходом векторных признаков (нужен пакет onnx). Выполните experiment.v24.train encode и experiment.v24.train fit через python -m. Документные наборы восстанавливаются по SHA256 каждого текста и сверяются с хешами исходных обучающих файлов.
