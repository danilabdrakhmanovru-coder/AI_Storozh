# ИИ-сторож

## Конкурсный режим v11 (CPU)

Для проверки по ТЗ установите зависимости и запустите API из корня репозитория:

~~~powershell
pip install -r requirements.txt
python -m uvicorn app.main:app --host 127.0.0.1 --port 8001
~~~

Тестовая форма доступна по адресу http://127.0.0.1:8001/static/agent-test.html. Интеграция вызывает POST /v1/check. В v11 дополнительный классификатор различает просьбу снять защиту ассистента, обычный вопрос и другие обращения. Он уточняет спорные категории и снимает часть ложных блокировок. Все модели конкурсного режима работают локально на CPU. Полномочия задаются в security_policy.yaml. ## Загрузка датасета жюри

На странице `/static/agent-test.html` выберите файл в разделе «Проверка датасета», нажмите «Проверить файл» и скачайте predictions.jsonl. Допустимы UTF-8 JSONL, CSV организаторов (context содержит JSON) и ZIP с одним набором. В архиве с парой dev.csv/dev.jsonl используется dev.jsonl. Остальные материалы официального ZIP, включая программу оценивания, не исполняются.

Через HTTP передайте содержимое файла как тело запроса. Пример для PowerShell:

~~~powershell
curl.exe --fail "http://127.0.0.1:8001/v1/datasets/check?format=zip" -H "Content-Type: application/octet-stream" -H "X-API-Key: $env:STOROZH_DATASET_KEY" --data-binary "@public_dataset.zip" -o predictions.jsonl
~~~

Для закрытого JSONL укажите `format=jsonl` и имя своего файла. В строке обязательны уникальный строковый id, user_prompt и context с target_agent и user_role. Поля разметки необязательны и не передаются модели. Файл проверяется целиком на корректность до начала инференса. Лимиты — 10 000 записей и 32 МиБ для входного и распакованного файла.

Ответ имеет тип application/x-ndjson. Порядок и id соответствуют входу; X-Total-Rows содержит ожидаемое число строк, X-Policy-Version фиксирует версию политики на весь прогон. Ответы содержат decision, risk_category, risk_level, explanation, latency_ms. При технической ошибке строки возвращается id и _error без decision. После обрыва проверьте число строк и повторите запрос, если файл неполон. Внутренние задержки этого маршрута не заменяют официальный последовательный замер POST /v1/check.

Для внешнего стенда настройте серверный STOROZH_DATASET_KEY и передайте проверяющему этот ключ. Он действует на загрузку набора; обычный клиентский ключ приложения не может подставлять роли из файла. Поддерживается также ключ оператора. В локальном демонстрационном режиме на loopback ключ не обязателен. Сервис держит содержимое файла в памяти на время запроса; пакетный маршрут не добавляет строки в демонстрационный журнал и не вызывает целевого агента. Ссылка localhost доступна только на машине сервера.

## Дополнительный интерфейс с Qwen

Локальный защитный шлюз перед ИИ-агентом: правила безопасности + свой классификатор v2 + смысловая проверка Qwen через Ollama. Решения: `allow`, `confirm`, `block`. Модель не отменяет запреты правил.

## Запуск (Windows / PowerShell, Python 3.10+)

```powershell
pip install -r requirements.txt
ollama list
# Если модели ещё нет: ollama pull qwen2.5:7b
# Если Ollama не запущена: ollama serve
python -m uvicorn app.main:app --host 127.0.0.1 --port 8001
```

Интерфейс: http://127.0.0.1:8001 · API: http://127.0.0.1:8001/docs

Фронтенд: HTML/CSS/JavaScript без сборки и внешних CDN. Бэкенд: FastAPI/Pydantic, SQLite WAL, urllib для локальной Ollama. Файлы модели заранее устанавливаются в Ollama. Во время работы внешние API не требуются. Python и Ollama должны работать на одном компьютере при стандартной конфигурации.

## Пользовательский путь

1. Введите инструкцию, роль, источник и при необходимости вызов инструмента. Можно выбрать один из четырёх примеров.
2. Нажмите «Проверить инструкцию». Сначала правила проверяют текст, аргументы и полномочия. Классификатор v2 оценивает текст, затем Qwen анализирует запрос с контекстом. Шлюз выбирает самое строгое решение. В карточке и журнале сохраняются все три оценки. Целевой агент ещё ничего не получает.
3. Прочитайте краткий вывод и раскрываемые проверки: целостность инструкций, защита данных, безопасность действий, права и политики. Оценка 0–100 — сигнал риска, не вероятность атаки.
4. `block` останавливает передачу. `confirm` ожидает оператора. После сбоя модели или правил подтверждение не заменяет повторную проверку.
5. `allow` или подтверждённый запрос можно отдельно передать демо-агенту. Сервер использует сохранённый текст и атомарно помечает попытку отправки, предотвращая повторную отправку. Демо-агент отвечает через Ollama без файлов и инструментов.
6. В журнале можно открыть запрос, подтвердить/отклонить, посмотреть ответ и отметить верное решение, ложное срабатывание или пропущенную атаку.
7. В отчётах выберите даты (по локальному времени браузера, последний день включительно). HTML содержит краткий вывод, частые категории, технические сбои и отметки качества; его можно распечатать в PDF. CSV содержит записи без исходных текстов запросов. Даты в выгрузке — UTC.

## Настройки окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `OLLAMA_URL` | `http://127.0.0.1:11434` | Адрес вашей Ollama |
| `OLLAMA_MODEL` | `qwen2.5:7b` | Модель проверки |
| `OLLAMA_TIMEOUT` | `60` | Предельное ожидание ответа, секунды |
| `TARGET_MODEL` | та же модель | Модель демо-агента в отдельном диалоге |
| `STOROZH_MODEL_ENABLED` | `true` | `false` отключает Qwen и удерживает запрос до полной проверки |
| `STOROZH_API_KEY` | не задан | Ключ оператора |
| `STOROZH_CLIENTS_JSON` | `{}` | Серверная привязка клиентских ключей к идентичности |
| `STOROZH_DB` | `audit.db` | SQLite-файл |
| `STOROZH_POLICY` | `policy.yaml` | Файл политики |

Настройки читаются при запуске; после изменения перезапустите сервер. Первый ответ Qwen может быть медленным из-за загрузки весов. Одновременно выполняется одна смысловая проверка; при занятости новая проверка получает `confirm` с техническим статусом, без возможности разрешить непроверенный запрос. Не используйте несколько uvicorn workers: политики и ограничитель модели рассчитаны на один процесс.

## Доверие и интеграция

Без ключей доступна только локальная операторская демонстрация. Выбор роли в ней — симуляция пользователя, а не система регистрации. Запросы с другого Origin и чужого Host отклоняются. Для реальной интеграции настройте ключ оператора и отдельные клиентские ключи:

```powershell
$env:STOROZH_API_KEY = '<случайный-секрет-оператора>'
$env:STOROZH_CLIENTS_JSON = '{"<случайный-ключ-приложения>":{"user_id":"alice","role":"analyst"}}'
python -m uvicorn app.main:app --host 127.0.0.1 --port 8001
```

Передавайте ключ заголовком `X-API-Key`. Для клиентского ключа `role` и `user_id` из тела запроса игнорируются: сервер берёт их из конфигурации. Только оператор может менять политику, читать общий журнал и отчёты, подтверждать запросы и оценивать решения. Ключи нельзя помещать в фронтенд публичного сайта; клиентские ключи предназначены для серверов интеграции. Операторский ключ даёт право симулировать пользователей в панели.

`POST /check` принимает `{text, source, tools:[{name,args}]}`. `role` и `user_id` разрешены как параметры операторской симуляции. `source` — `user`, `document`, `tool_output`, `web`; его должен устанавливать доверенный интегратор по реальному происхождению текста.

Ответ содержит `request_id`, `decision`, `risk`, `summary`, `checks`, `reasons`, `model`, `identity`, `policy_version`, `can_review`, `can_forward`.

- `GET /requests/{id}` — сохранённое решение и текущий жизненный цикл.
- `POST /confirm/{id}` с `{approve:true|false}` — решение оператора. Повторные и просроченные подтверждения запрещены; срок 1 час.
- `POST /dispatch/{id}` — демонстрационная доставка разрешённого текста в Ollama. Нельзя заменить текст при отправке. После изменения политики нужна повторная проверка. Сбой отправки не вызывает автоматического повтора.
- `POST /check/batch` — 1–20 запросов, последовательно.
- `GET /logs?start=<unix>&end=<unix>&decision=block&n=20&offset=0` — фильтры и страницы.
- `PUT /requests/{id}/feedback` — `{label:"correct"|"false_positive"|"missed_attack",note:"..."}`.
- `GET /reports?start=<unix>&end=<unix>` — агрегаты за полуоткрытый период `[start,end)`.
- `GET /reports/export?...&format=html|csv` — выгрузка. CSV защищён от формул в пользовательских ячейках.
- `GET/PUT /policy`, `GET /config`, `GET /health`, `GET /selftest`.

Для другого LLM-агента интегратор обязан проверять инструкцию до вызова модели, проверять каждый фактически запланированный вызов инструмента и сам обеспечивать удержание `confirm`/`block`. Защита не может остановить прямое обращение к агенту в обход шлюза. Демо `/dispatch` намеренно не исполняет инструменты. Произвольный внешний URL в теле запроса не поддерживается.

## Архитектура и данные

- `app/guard.py` — нормализация, правила, проверка политики и полномочий.
- `app/model.py` — адаптер Ollama, JSON Schema и строгая валидация ответа, тайм-аут.
- `app/storage.py` — транзакции SQLite, сохранённые запросы, подтверждения, выгрузки и метрики.
- `app/main.py` — API, доверенная идентичность, объединение оценок, шлюз передачи.
- `static/` — адаптивный операторский интерфейс.

Новая история хранится в таблице `requests`. Старая таблица `log` из версии 0.2 сохраняется без изменений и не смешивается с новыми метриками: в старых записях нет полного жизненного цикла. SQLite содержит полные исходные тексты и аргументы — доступ к файлу базы нужно ограничить средствами ОС. Автоматической очистки/маскирования нет. В отчёт исходные тексты не экспортируются.

Отчёт считает первоначальные решения в выбранном периоде. Состояния, подтверждения и отзывы — на момент выгрузки. Частые срабатывания не доказывают наличие атак. Ошибки классификации учитываются только по отметкам оператора; доля точности без независимой разметки не заявляется.

## Проверки

```powershell
pip install -r requirements-dev.txt
python tests/run_all.py
# Отдельные наборы:
python tests/rules/test_guard.py
python tests/api/test_api.py
node --check static/app.js
```

29 исходных сценариев ядра; API-тесты используют временную базу/политику и тестовую замену модели. Они проверяют запрет передачи, подтверждение и его срок, повторные отправки, сбои модели/агента, привязку ролей к ключам, изменение политики, вложенные идентификаторы владельца, отчёты и экспорт. API-тесты не измеряют качество настоящего Qwen. Реальные прогоны интерфейса и локальной модели описаны в `VALIDATION.md`.

## Границы прототипа

Это работающий прототип, а не гарантия обнаружения всех атак. Проверка владельца по аргументам не заменяет row-level access control в базе и файловые ACL. Обфускация и семантические атаки требуют независимого расширенного тестирования. Нет обучения своей модели, многопользовательского входа, распределённой очереди, rate limiting по клиентам и автоматической ротации журнала. Для публичного развёртывания потребуются эти механизмы, TLS и управление секретами. В текущем виде запускайте как локальный стенд.

Формат интеграции Ollama: https://docs.ollama.com/api/chat и https://docs.ollama.com/capabilities/structured-outputs.
